How the workflow works

The big picture

The harness has three top-level commands and eight role-based agents. Commands are orchestrators: they don't write code themselves; they bring agents onto a team, brief them, route messages, and dispatch one-shot sub-agents against GitHub-issue state — backed by pure-shell discovery scripts (task-finder.sh + nine per-stage helpers) that decide what's eligible each pass. Every meaningful state transition is recorded as a GitHub issue label flip, which means the loop can be stopped, resumed, or re-run without losing track of where work is.

Discovery vs. execution

There are two distinct phases, and they don't share state in memory — they share state through git and GitHub. Discovery produces documents; execution consumes those documents and produces code.

Discovery documents

Run once per feature, before any code lands. The user converses with product-owner until the requirement is locked, then with design-lead until the visual language + surface/navigation inventory are locked, then with architect until the technical decisions are locked. Each interviewer is read-only; writer teammates (doc-writer instances) commit the artifacts. The phase ends with a single PR titled feature-lockin.

  • /deep-dive-feature — PRD + critical path + glossary + design system + surface/nav inventory + ADRs + implement-detail + per-entity api-contract / data-model files
  • /scaffold-project — greenfield only; reads the ADRs and brings up a bootable stack, seeding the locked design tokens

Execution code

Run repeatedly per feature, idempotently, against GitHub-issue state. The orchestrator runs task-finder.sh once per pass — pure shell, no LLM — to find every eligible candidate across nine stages, then processes the report top-to-bottom, dispatching one-shot sub-agents per stage. Each stage is self-skipping and label-scoped, so a single pass safely advances whatever is ready. Wrap with /loop for unattended end-to-end shipping.

  • /implement-feature <feature-name> drives task → slice → PR lanes
  • Dispatches background agents — engineer, e2e-author, reviewer
  • Every dispatch is a one-shot sub-agent; nothing is held in memory between passes

The agents

Eight role-based subagents under agents/. Each one is briefed by a command or a workflow skill, never by the user directly. Roles are sharp on purpose: product-owner never writes architecture; design-lead never writes code; engineer never writes E2E specs; reviewer is read-only on production code.

Discovery — /deep-dive-feature

Three sequential phases (product → design → architecture). The orchestrator grows the team one teammate at a time: it does not pre-create writers until the interviewer they answer is ready to hand off a dispatch payload.

STEP 1–4

Phase 1: product

product-owner + user
  • Orchestrator spins up a team with one teammate
  • User talks to product-owner directly
  • User "locks requirements" explicitly
  • Product owner composes a scoped dispatch prompt, names the kebab-case feature
STEP 5–6

Phase 1 publish

orchestrator + requirement-writer
  • Orchestrator creates a milestone and a worktree-backed branch docs/<feature-name>
  • Invites requirement-writer (subagent_type = doc-writer)
  • Writer pulls payload from product-owner via SendMessage
  • Writer commits PRD, critical-path, glossary updates
STEP 6A–6D

Phase 1.5: design

design-lead + user + design-writer
  • Orchestrator invites design-lead after the requirement is published
  • User talks to design-lead directly
  • Locks the visual language + the surface / navigation inventory
  • design-writer commits docs/design-system/{overview,tokens,components,accessibility}.md + surfaces.md
STEP 7–9

Phase 2: architecture

architect + user
  • Orchestrator invites architect
  • User talks to architect directly
  • User "locks decisions" explicitly
  • Architect composes four scoped dispatch prompts
STEP 10

Phase 2 publish

orchestrator + 4 writers
  • Orchestrator invites four doc-writer instances
  • Each writer pulls its scope-appropriate payload from architect
  • Implement-detail, ADRs, api-contracts, data-models are committed
STEP 11

Lock in

orchestrator
  • Push the docs/<feature-name> branch
  • Open a single PR labeled feature-lockin
  • User reviews and merges manually — discovery is done
GUARDRAILS

What the orchestrator does not do

policy
  • Never answers product questions itself
  • Never answers for the user — interviewer questions reach the human verbatim
  • Never skips a lock gate
  • Never invites writers ahead of their interviewer

Scaffold — /scaffold-project

Optional, runs once on a greenfield project (the skill aborts if any of backend/, frontend/, a compose file, or e2e/ already exists). Reads stack and topology decisions from docs/architecture-decision-record/ and materializes a bootable skeleton from templates. Ends in its own PR.

  1. Confirm greenfield — all four surfaces (backend, frontend, compose, e2e) must be missing.
  2. Read the ADRs to pick backend / frontend stack variants and the compose service list.
  3. Create chore/scaffold-project.
  4. Materialize backend → commit. Materialize frontend → commit. Materialize docker-compose.yaml → commit.
  5. Boot check: docker compose up -d --build, probe each framework-metadata endpoint, then docker compose down. Stops on failure — does not mutate templates to mask a broken boot.
  6. Materialize Playwright e2e → npm install → commit.
  7. Materialize the CI pipeline + CI-parity pre-push hook → commit.
  8. Assert the design system exists: docs/design-system/tokens.md and surfaces.md must be present (locked upstream by design-lead during /deep-dive-feature). Fails loudly if absent — scaffold consumes the design system, it does not generate it.
  9. Translate the locked tokens.md into frontend/src/styles/tokens.css and import it from the frontend entry → commit. (The ## Design taste section of CLAUDE.md is already authored by design-writer — scaffold doesn't re-write it.)
  10. Push and open the PR.

Execution — /implement-feature <feature-name>

One sweep through nine lifecycle stages, in order. The orchestrator runs skills/operation-git/scripts/task-finder.sh <feature-name> once — pure shell, no LLM — to discover every eligible candidate across all nine stages against ONE GitHub-state snapshot, then walks the report top-to-bottom. Each stage is milestone-scoped (the script filters by feature name on every gh query), label-driven (picks up whatever has the right labels right now), and self-skipping (the stage's report section reads - (none) when there's nothing to do). One invocation = one pass — wrap with /loop to keep advancing until the feature ships.

The orchestrator does not wait for backgrounded agents. Once a stage dispatches its agents, the orchestrator moves on; the agents push commits and flip labels asynchronously, and the next pass picks them up.

Task lane

1

kickoff-slice

label flip
  • Picks slices with level:slice + kind:feature + status:ready-to-implement
  • Skips any with open Blocked by
  • Flips slice → status:in-progress
  • Adds status:ready-to-implement on every task sub-issue
2

implement-task

dispatch
  • Picks unblocked tasks with status:ready-to-implement
  • Locks each with status:in-progress
  • Dispatches engineer (Mode A) or e2e-author by type:*
  • Agent commits, pushes, adds review:pending
3

review-task

dispatch
  • Picks tasks with review:pending
  • Flips the gate to review:running
  • Dispatches a one-shot reviewer per task
  • On review:passed the reviewer also closes the task; on review:need-fix the verdict stays
4

fix-task

dispatch
  • Picks tasks with review:need-fix (gate not review:running)
  • Strips the need-fix label (the lock)
  • Dispatches engineer (Mode C) or e2e-author
  • Agent fixes, pushes, re-adds review:pending

Slice lane

5

prepare-slice

dispatch
  • Picks slices whose task sub-issues have all closed and have no review:* / e2e:* yet
  • Locks slice with e2e:running
  • Dispatches engineer (Mode D) to run the slice's E2E specs against a live stack
  • On green: removes e2e:running, adds sticky e2e:validated + review:pending on the slice. On test-case constraint: status:need-attention
6

review-slice

dispatch
  • Picks slices with review:pending
  • Dispatches reviewer
  • On pass: reviewer opens the draft PR with Closes #<slice-#> body
  • On fail: review:need-fix
7

fix-slice

dispatch
  • Picks slices with review:need-fix
  • Dispatches engineer to fix findings + re-validate E2E
  • Re-adds review:pending on success

PR lane

8

fix-pr

dispatch
  • Picks draft PRs with failing CI and/or merge conflicts (no in-flight lock)
  • Locks with status:fix-in-progress
  • Dispatches engineer (Mode B) with the scenario set
9

close-pr

merge
  • Picks MERGEABLE draft PRs with all CI green and merge:auto
  • Promotes draft → ready, squash-merges, deletes the branch
  • GitHub auto-closes the slice via the Closes #<slice-#> body
  • merge:manual PRs are left for the user to merge
LOOP

Wrap to keep advancing

recommended
  • /loop /implement-feature <feature-name>
  • Each pass picks up whatever moved since the last pass
  • Backgrounded agents finish on their own schedule; a finished agent re-invokes the orchestrator, which closes that agent's tracking task by owner at pass entry
  • Resumable: the loop survives interrupts because labels are the state

Labels are the protocol

Agents don't share memory. They share GitHub labels. Every dispatch is keyed on a label combination; every terminal action is a label flip. That's why the lifecycle survives crashes, context limits, and user interruptions — the next pass just reads the labels and re-derives where work is.

level:*

  • level:slice — a vertical user-visible increment
  • level:task — a single typed unit of work

kind:*

  • kind:feature — full lifecycle today
  • kind:bug / kind:enhancement — issue-tracked but not yet looped

type:* (tasks)

  • type:e2e — Playwright, owned by e2e-author
  • type:backend / type:frontend — owned by engineer

status:*

  • status:ready-to-review — human approval gate
  • status:ready-to-implement — orchestrator picks this up
  • status:in-progress — orchestrator's lock
  • status:fix-in-progress — PR-level lock
  • status:need-attention — agent bailed; human owns the next move

review:*

  • One gate per issue (task or slice) — covers code + security in one pass
  • review:pending — reviewer dispatch armed
  • review:running — reviewer in flight
  • review:passed / review:need-fix — verdicts
  • fix-* skills only fire when the gate is not review:running

merge:* / e2e:* / lockin

  • merge:auto / merge:manual — close-pr behavior
  • e2e:running — prepare-slice lock
  • e2e:validated — sticky; set on E2E pass, keeps prepare-slice from re-adopting
  • feature-lockin — the discovery PR

Two cross-cutting rules emerge from the diagrams. (1) The presence of a review:running or e2e:running label is the in-flight lock — fix skills refuse to dispatch while a reviewer or validator is still working. (2) The absence of any review:* label is what unblocks fix-task / fix-slice after they strip need-fix — the agent re-adding review:pending is what re-enters the review loop.

Who talks to whom

Two distinct channels: a Team-shared channel for the interactive discovery agents (product-owner, design-lead, architect, doc-writer instances) and a one-shot dispatch channel for the lifecycle agents (engineer, e2e-author, reviewer).

Team mode

discovery (deep-dive-feature)

TeamCreate spins up named teammates that can SendMessage each other. The orchestrator grows the team one teammate at a time. Writers pull dispatch payloads from interviewers via SendMessage — the orchestrator never forwards artifacts inline.

  • product-owner ↔ user (direct)
  • product-owner ↔ requirement-writer (pull payload)
  • design-lead ↔ user (direct)
  • design-lead ↔ design-writer (pull payload)
  • architect ↔ user (direct)
  • architect ↔ 4 writers (pull scoped payloads)

Dispatch mode

execution (/implement-feature stages 1–9)

/implement-feature runs task-finder.sh once per pass to discover candidates, then issues one Agent call per eligible unit of work. The agent runs to completion in the background, makes its commits, pushes, and flips its terminal label. No shared memory; no back-and-forth conversation.

  • Skill → engineer (one-shot, per task / slice / PR)
  • Skill → e2e-author (one-shot, per E2E task)
  • Skill → reviewer (one-shot, per task or slice)
  • Agent → GitHub (commits, comments, label flips)

Hook mode

engineer worktree pushes

engineer-pre-push.sh fires as a PreToolUse hook on every Bash call. It no-ops unless the command contains git push in an engineer worktree. On a real push it runs the lint / type / security / test gate for the relevant stack and denies the push on failure.

  • Hook → engineer (deny / allow)
  • Engineer reads the denial summary, fixes, retries the push

Where the user sits

The user is in the loop in three specific places — and intentionally out of the loop everywhere else.

MomentWhyWhat the user does
discovery interview Only the user knows what they want to build. product-owner, design-lead, and architect talk to the user directly — the orchestrator does not interpose, paraphrase, or guess. Answers questions. Says "lock requirements" / "lock the design" / "lock decisions" when ready.
PR review Every workflow ends with a PR. Discovery PRs (feature-lockin) and scaffold PRs require a human merge. merge:manual slice PRs (reviewer's default) too. Reviews, requests changes via comments, merges manually — or relabels to merge:auto to let close-pr land it.
status:need-attention Agents bail rather than guess when an E2E spec rewrite is needed or scope is ambiguous. The lifecycle stops on that slice / PR until the human clears the label. Edits the spec / clarifies scope / removes the label so the next pass picks the work up.

Everywhere else — task dispatch, code review, security review, fix loops, draft PR creation, merge of merge:auto PRs — the user can step away. The loop reads labels, dispatches one-shot agents, and advances. /loop /implement-feature <feature-name> keeps it going until the feature is shipped or until something hits status:need-attention.
